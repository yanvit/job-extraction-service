# Job Extraction Service

Кейс 1 курсу AI Engineering: сервіс витягує структуровані дані з «брудних» текстів вакансій українського ринку праці за схемою `JobPosting`, порівнює провайдерську (Claude) і локальну (Ollama) моделі та обґрунтовує вибір для продакшну цифрами. Звіт: [REPORT.md](REPORT.md).

**Результат:** у продакшн обрано **Claude Haiku 5.5 + промпт v2**. Показники на golden set:
- точність по полях 0.985;
- 100% валідних відповідей;
- p95 6.5 с;
- $1.03 за 1000 документів.

Для порівняння: локальна qwen2.5:3b дає 0.75, Claude Haiku 4.5 — 0.935 при цілих $7.2 за 1000 документів. Деталі в [REPORT.md](REPORT.md).

**ДЗ2 (RAG + evals)** — у тому ж репозиторії. Відповіді на питання про IT-вакансії, зарплати DOU, Дія Сіті і ФОП з цитатами на кожне твердження: 160 документів, hybrid search + rerank, Claude Haiku 5.5.
- На 29 питаннях: «не знаю» там, де треба, — 100%; правильне джерело — 100%; LLM-суддя — 0.955.
- $0.55 на 1000 питань; evals у CI.
- Запуск: `make rag`. Карта вимог — [нижче](#дз2-де-що-шукати), звіт — [REPORT.md](REPORT.md).

## Швидкий старт

Потрібно: **Python 3.11+**, ключ Anthropic API, [Ollama](https://ollama.com/download) з моделлю `qwen2.5:3b`.

```bash
python3 -m venv .venv && source .venv/bin/activate
make install                     # pip install -r requirements.txt
cp .env.example .env             # впишіть ANTHROPIC_API_KEY
ollama pull qwen2.5:3b           # ~2 ГБ; Ollama має бути запущена (застосунок або `ollama serve`)
make check                       # перевірка ключа і Ollama

make run                         # = python main.py: усі прогони -> метрики -> таблиці в REPORT.md
```

- `make run` проганяє всі 34 тексти через матрицю з `config.yaml`. Найдовша частина — локальна модель (~30–40 хв на MacBook M1 Pro). Відповіді кешуються в `results/cache/`, тож повторний запуск миттєвий і безкоштовний.
- `make quick` робить те саме лише на golden set (10 текстів), це кілька хвилин.
- `make report` перераховує метрики й таблиці з уже збережених `results/runs/` без жодного виклику моделей.
- Вартість повного прогону Claude: менше $0.10 для Haiku 5.5; Haiku 4.5 приблизно в 10 разів дорожча.

Інші команди: `make regress` (регресія промптів v1 → v2 на golden set), `make golden` (перевірка розмітки), `python -m jobex.extract_one data/raw/job_15.txt --model qwen2.5-3b-local --sampling t0` (одна модель на одному тексті).

## Як це працює

```
data/raw/*.txt → prompts/vN (system + user) → модель (config.yaml) зі structured output
   → Pydantic-валідація → ok | 1 спроба виправлення з текстом помилок → repaired | failed
   → results/runs/<модель>__<промпт>__<семплінг>.jsonl (модель, версія промпту, семплінг, токени, час, вартість)
   → метрики на golden set → results/metrics.{json,csv}, results/golden_diff.md, таблиці в REPORT.md
```

- **Схема** (`jobex/schema.py`): 12 полів, 8 enum, вкладений `salary`, списки об'єктів `skills` і `languages`. Усі поля обов'язкові: «немає даних» = явне `null`/`[]`/`unknown`.
- **Моделі** (`jobex/clients/`): спільний інтерфейс `LLMClient`.
	- Claude через офіційний SDK з нативною JSON Schema (`output_config.format`) і fallback на tool use.
	- Ollama через `/api/chat` з `format` = JSON Schema.
	- Ретраї (експоненційний backoff + jitter на таймаут/429/5xx/529) і таймаути — спільні.
- **Конфіг** (`config.yaml`): моделі з цінами, профілі семплінгу (`t0`, `t07_p09`), матриця експерименту. Claude Haiku 5.5 не приймає `temperature`/`top_p`, тому для неї один прогін `api_default`, а порівняння семплінгу — на Haiku 4.5 і qwen.
- **Промпти** (`prompts/`): версії `v1`, `v2` з `meta.yaml` і [CHANGELOG](prompts/CHANGELOG.md).
- **Golden set** (`data/golden.jsonl`): 10 розмічених вакансій, правила — [data/LABELING.md](data/LABELING.md).

## ДЗ2: chunking-стратегія і чому саме вона

Корпус RAG складається з двох різних за природою типів документів:
- **149 вакансій (Markdown)**: короткі, 1–11 тис. символів, з чіткими розділами «Вимоги», «Обов'язки», «Ми пропонуємо», «Метадані Djinni». Медіана розділу ~400 символів.
- **11 довідкових документів (HTML, PDF)**:
    - закон про Дія Сіті (розділи → статті; стаття до 27 тис. символів);
    - звіти DOU про зарплати (підрозділи за містами, мовами, рівнями);
    - презентаційні PDF KPMG/PwC (сторінка = слайд = одна тема);
    - статті й гайди.

**Стратегія — structure-aware (по розділах)** (`rag/chunking.py`):
1. **Різати по заголовках.** Документ ділиться на розділи за заголовками зі збереженим шляхом (`Розділ I > Стаття 1`, `Вакансія > Requirements`). Питання до цього корпусу зазвичай стосуються одного розділу: «що вимагає вакансія», «що каже стаття 5», «скільки отримує Go-розробник».
2. **Не розривати блоки.** Блоки розділу (абзаци, пункти, рядки таблиць) пакуються в чанк до **1200 символів** і ніколи не розриваються. Лише блок понад 1400 символів ріжеться по реченнях.
   - 1200 символів ≈ 300–400 токенів для змішаного UA/EN тексту. Це вміщується в ліміт 512 токенів мультимовних embedding-моделей разом із заголовком.
   - Майже всі розділи вакансій і слайди вміщуються цілком.
3. **Злити замалі розділи.** Розділи коротші за **300 символів** зливаються з наступним, щоб не було чанків «Ми пропонуємо: — Гнучкий графік».
4. **Додати контекстний заголовок.** До тексту для ембеддингу й BM25 додається «назва документа › розділ [вакансія, стек: Go]». Чанк «- Docker, Kubernetes» без нього не знає, з якої він вакансії.
5. **Метадані кожного чанка:**
   - джерело (URL), назва, розділ, сторінки (PDF);
   - тип документа, мова, версія/дата, ліцензія;
   - хеш документа і хеш чанка;
   - для вакансій — стек.

**Порівняння з фіксованим розміром** (1000 символів, перекриття 200), `make chunks` → [`data/processed/chunking_comparison.md`](data/processed/chunking_comparison.md):

| Метрика | Structure-aware | Fixed 1000/200 |
|---|---|---|
| Чанків | 849 | 899 |
| Медіана / p95, символів | 812 / 1191 | 1000 / 1000 |
| Починається посеред речення | 2.9% | 61.5% |
| Межа чанка розрізає абзац / пункт | 0.9% | 78.3% |
| Захоплює ≥2 розділи | 0% | 57% |
| Має розділ у метаданих (для цитати) | 98.4% | 0% |
| Крихітних (< 200 символів) | 36 | 0 |

- **Що дає фіксоване вікно.** Більше половини чанків змішують два розділи: кінець «Вимог» і початок «Ми пропонуємо», або дві статті закону. Майже кожен чанк розрізає абзац. Для цитування «документ + розділ», якого вимагає крок 3, у такого чанка взагалі немає розділу.
- **Ціна structure-aware.** Розміри нерівномірні, є 36 коротких хвостів (переважно кінцівки вакансій із метаданими Djinni).
- **Якість пошуку для обох стратегій** виміряно в наступному розділі.

## ДЗ2: індекс, hybrid search і якість пошуку

`make index` → `make eval-retrieval`:
- **Ембеддинги:** `intfloat/multilingual-e5-small` (локально, 384 виміри, UA/EN), кеш на диску за sha256 тексту. Безкоштовно, ~20 с на весь корпус на CPU.
- **Векторна база:** Qdrant у локальному режимі (`data/index/`), метадані чанка в payload.
- **Лексичний пошук:** власний BM25 (`rag/bm25.py`); токенізатор зберігає `c#`, `c++`, `node.js`.
- **Hybrid:** Reciprocal Rank Fusion (k=60) по топ-30 з кожного пошуку. RRF дивиться лише на місця в списках, тож бали BM25 і косинуса не треба зводити до однієї шкали.
- **Reranking:** мультимовний cross-encoder `mmarco-mMiniLMv2-L12` переоцінює топ-20 після fusion.
- **Фільтри за метаданими:** `doc_type`, `lang`, `doc_id`, `stack` (для вакансій), напр. `python -m rag.search "досвід з Kafka" --doc-type vacancy --stack Java`.

**Як міряли.** 15 питань у [`evals/retrieval_questions.yaml`](evals/retrieval_questions.yaml): закон і огляди Дія Сіті, ФОП 3 групи, дві хвилі DOU, вакансії; українською та англійською; 4 з пастками (інша хвиля опитування з тим самим розділом, кілька схожих вакансій).
- Правильний чанк задано правилом «документ + фраза-відповідь у тексті», а не `chunk_id`, тому ті самі питання працюють для обох стратегій чанкінгу.
- Фрази перевірено вручну. Після першого прогону кожну фразу шукали по всьому корпусу й дописали пропущені правильні джерела: стаття НААУ дослівно повторює вимоги закону, а Riverpod/BLoC вимагають три Flutter-вакансії, а не одна.
- recall@k = частка питань, у яких хоча б один правильний чанк є в топ-k. MRR рахується по топ-10.

| Чанки | Конфігурація | recall@1 | recall@3 | recall@5 | MRR | мс/запит |
|---|---|---|---|---|---|---|
| structure | лише векторний | 0.73 | 0.87 | 0.93 | 0.815 | 58 |
| structure | лише BM25 | 0.53 | 0.93 | 0.93 | 0.700 | 1 |
| structure | hybrid (RRF) | 0.67 | 1.00 | 1.00 | 0.822 | 33 |
| structure | **hybrid + rerank** | **0.80** | **1.00** | **1.00** | **0.900** | 389 |
| structure | hybrid + rerank + фільтр | 0.80 | 1.00 | 1.00 | 0.900 | 339 |
| fixed 1000/200 | лише векторний | 0.67 | 0.80 | 0.87 | 0.767 | 36 |
| fixed 1000/200 | hybrid (RRF) | 0.80 | 0.80 | 0.93 | 0.837 | 38 |
| fixed 1000/200 | hybrid + rerank | 0.73 | 0.93 | 1.00 | 0.839 | 393 |

Повна таблиця з місцем правильного чанка для кожного питання: [`evals/results/retrieval.md`](evals/results/retrieval.md).

**Висновки:**
- **Обрано structure-aware + hybrid + rerank.** Найкращий MRR (0.90), і правильний чанк завжди в топ-3. Для RAG у контекст підемо з топ-5, тож recall@5 = 1.00 важливіший за recall@1.
- **Hybrid важливий для обох видів запитів.** BM25 сам по собі слабкий (0.53 @1): немає стемінгу для української, тож «працівників» і «працівники» для нього різні слова. Зате він знаходить точні терміни й числа (`Tokio`, `ФОП 3 групи`, «12 календарних місяців»), де вектор плутає сусідні статті закону (q04: BM25 ставить правильний чанк першим, вектор — сьомим; hybrid дає 2, після rerank — 1).
- **Reranker виправляє порядок.** Він піднімає recall@1 з 0.67 до 0.80 і MRR з 0.82 до 0.90 ціною ~0.35 с на запит.
- **Structure-aware проти fixed — чесно.** На recall@1 fixed-чанки не гірші: перекриття дублює факти, і їх простіше «зачепити». Але з reranker-ом structure-aware дає кращий MRR (0.90 проти 0.84) і recall@3 (1.00 проти 0.93). Головне ж — кожен чанк має розділ для цитати, а 57% fixed-чанків змішують два розділи. Для відповіді з джерелами (крок 3) це вирішальне.
- **Фільтр за `doc_type` тут нічого не додав:** правильні джерела вже нагорі. Він потрібен для запитів на кшталт «вакансії Java з Kafka», де без фільтра конкурують звіти DOU.
- **Обережно з цифрами:** 15 питань — це грубий сигнал, одне питання = 0.067. Різниця між конфігураціями в 1 питання — не доказ.

**Характерні промахи (hybrid + rerank):**
- **q10, q11 — не та хвиля опитування.** Питання про зиму 2026, а першим іде такий самий розділ літньої хвилі (і навпаки). Обидва звіти мають тип `report`, тож фільтр за типом не рятує. Що покращити: розпізнавати в питанні «зима/літо 2026» і фільтрувати за полем `version`.
- **q02 — сусідній чанк того самого документа.** Першим іде чанк НААУ про бронювання, а не про вимоги; правильний на 2 місці. Для RAG з топ-5 це не проблема.


## ДЗ2: RAG з джерелами

```bash
make ask Q="Який річний ліміт доходу ФОП 3 групи у 2026 році?"
python -m rag.answer "Які Java-вакансії вимагають Kafka?" --doc-type vacancy --stack Java
python -m rag.answer "..." --json      # джерела, бали, токени, вартість, версія і хеш промпту
```

Код: `rag/answer.py`, налаштування — `rag/config.yaml` → `answer`, промпт — [`prompts/rag/v3/`](prompts/rag/v3/) (поточний; v1 → v2 → v3 з причинами — у [CHANGELOG](prompts/rag/CHANGELOG.md)).

**Як будується відповідь:**
1. **Пошук:** hybrid + rerank, топ-8 (найкраща конфігурація з кроку 2), опційно з фільтрами за метаданими.
2. **Контекст у межах бюджету:** 2500 токенів на джерела, приблизно 5–7 чанків. Чанки йдуть у порядку релевантності. Той, що не влазить, пропускається, бо наступний коротший може влізти. Чанки з балом нижче −2 не беруться зовсім. Кожне джерело має id `S1…Sn`, назву документа, розділ і версію. Версія потрібна, щоб модель розрізняла хвилі DOU.
3. **Відповідь:** Claude Haiku 5.5 зі structured output, JSON `{status, claims[{text, sources}], missing}`, де `status` — `answered`, `partial` або `not_found`.
4. **Перевірка цитат у коді:** твердження без жодного id із контексту викидається. Якщо не лишилось жодного, відповідь стає `not_found`. У відповіді показуються лише процитовані джерела, у форматі «документ › розділ — URL».

**«Не знаю» на двох рівнях:**
- **Поріг reranker-а, без виклику моделі.** Якщо найкращий чанк має бал нижче 1.5, відповідь — «у документах цього немає». Поріг узято з розподілу балів:
  - на 15 питаннях з відповіддю (крок 2) мінімум 2.88;
  - на питаннях поза темою («оренда у Львові», «чемпіонат з футболу») від −7.5 до −2.7;
  - на питаннях із суміжної теми, відповіді на які немає («єдиний податок ФОП 2 групи»), від 0.2 до 1.1.

  Це дешево (0 токенів) і детерміновано, а заодно відсікає prompt injection у питанні.
- **Модель.** Підступні питання з балом 5–8, наприклад «медіана DOU 2019» чи «вимоги Дія Сіті у 2030», поріг проходять: схожі розділи є, а потрібного періоду немає. Тут промпт вимагає `not_found` і не дозволяє підставляти цифри за інший період. На прикладах це працює: модель відповідає, що в джерелах є лише 2025–2026.
- **`partial`.** Якщо відповідь є лише на частину питання, модель дає її і окремо пише, чого в документах немає. Приклад: «вимоги до резидента + вартість реєстрації».

**Знахідки під час налаштування:**
- **Thinking з'їдає ліміт.** Haiku 5.5 спершу думає, і ці токени списуються з `max_tokens`. На 1024 складне питання обрізалось ще до JSON, тому тепер ліміт 4096. Обрізана відповідь позначається як `gate: error`, а не як чесне «не знаю».
- **Вартість і затримка (тестсет, 29 питань):** **$0.55 на 1000 питань**, відмови на порозі безкоштовні. Затримка p50 2.9 с, p95 13 с: складені питання довше через thinking.
- **Вада v1** (модель вписувала id джерела в текст, «(S4)») виправлена у v2. Інші зміни промпту виросли з розбору evals, див. CHANGELOG.

## ДЗ2: тестсет, evals і CI

```bash
make evals            # 29 питань → відповіді → метрики → пороги (exit 1, якщо нижче порогу)
make calibrate-export # лист для ручної оцінки відповідей → evals/calibration/sheet.yaml
make calibrate        # згода LLM-судді з ручною оцінкою → evals/results/calibration.md
make rag              # усе ДЗ2 однією командою: корпус → чанки → індекс → retrieval eval → evals
```

- **Тестсет** — [`evals/testset.yaml`](evals/testset.yaml), 29 питань. Кожне має еталонну відповідь, ключові факти, допустимі джерела і дослівну фразу-доказ з документа.
  - 17 питань з відповіддю.
  - 5 пасток: застаріла ставка військового збору, дві хвилі DOU з однаковими розділами, стара межа частки ФОП.
  - 7 без відповіді, серед них підступні («DOU 2019», «ФОП 2 групи», «зарплати в Польщі») і prompt injection.
- **Scoring** — [`evals/scoring.py`](evals/scoring.py), тести в [`evals/test_scoring.py`](evals/test_scoring.py).
  - **Детерміновані перевірки:**
    - «не знаю» там, де треба;
    - правильний документ серед процитованих;
    - ключові факти: цифри нормалізуються, «5%» не знаходиться в «15%»;
    - відсутність типової помилки пастки.
  - **LLM-суддя** (Claude Opus 5.5, промпти [`prompts/judge/v1/`](prompts/judge/v1/)): правильність проти еталону (correct / partial / incorrect).
  - **Faithfulness:** кожне твердження окремо перевіряється лише проти тих джерел, які воно саме цитує.
- **Калібрування судді** — [`evals/calibrate.py`](evals/calibrate.py). Лист містить реальні відповіді плюс навмисно зіпсовані, під нейтральними номерами. Скрипт рахує згоду і Cohen's κ.
- **Пороги** — [`evals/config.yaml`](evals/config.yaml). Результати: [`evals/results/metrics.md`](evals/results/metrics.md) і [`answers.jsonl`](evals/results/answers.jsonl); прогони v1, v2, v3 — у `evals/results/runs/`.
- **Кеш** — `evals/cache/`, лежить у git. Ключ — sha256 від моделі, промпту, питання і знайденого контексту. Повторний прогін без змін не викликає API. Змінили промпт — платимо лише за змінені пункти: ~$0.42 за повний прогін із суддею.
- **CI** — [`.github/workflows/evals.yml`](.github/workflows/evals.yml), на кожен push і PR: тести scoring → корпус → індекс → retrieval eval → evals з порогами. Потрібен секрет `ANTHROPIC_API_KEY` у налаштуваннях репозиторію.

Метрики, порівняння промптів і розбір помилок — у [REPORT.md](REPORT.md).
